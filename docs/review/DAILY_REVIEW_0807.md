## 一、这次最重要的案例:Redis 连接"Pong timeout"卡死排查全过程

### 现象
`chat_server` 跑一段时间后,Redis 相关操作全部卡死,日志里反复出现 `Error reading data from the server: Pong timeout.`,业务表现为"一开始正常,后面全阻塞在写 redis"。

### 排查过程(方法论比结论更值得记住)
1. **先怀疑 `cancel_after` 取消机制导致内部管道错位**——第一版怀疑方向,基于 Boost.Redis 官方 GitHub 上确实存在"取消操作与健康检查/管道顺序冲突"的已知 issue 类别
2. **新日志出现"上来啥都没干就 gg"**——直接推翻了"取消触发"这个假设,因为卡死发生在业务操作之前
3. **用 `redis-cli monitor` + `client list` 交叉验证**——决定性的一步:
   - `monitor` 显示 PING 规律发送,直到某个时间点后**彻底停止**(不是断了,是客户端不再发任何东西,包括自己的心跳)
   - `client list` 显示**同一个连接 id**,age/idle 持续增长,说明连接对象本身没有重建,是"卡死"不是"断开"
   - 这组合证据排除了网络问题、排除了服务端问题,精确定位到"客户端库内部状态卡死"
4. **`lsof` 确认 Boost.Redis 是纯头文件库**(没有 `.so`),排除"库版本没生效"这类干扰项
5. **最终定位真因:`redis_client_->conn_` 被多线程共享的 `io_context` 并发访问,没有 strand 保护**——`connection` 对象不像 `mysql::connection_pool` 那样提供 `thread_safe` 开关,默认假设单线程访问,多个 session 协程分布在不同线程并发调用 `async_exec`,直接把内部状态搞乱
6. **修复方案:把 redis 连接单独放到一个专属的单线程 `io_context` 上跑**,不与处理网络连接的多线程 `io_context` 混用——验证有效,问题消失

### 这次排查沉淀下来的通用方法论
- **先分清"是服务端问题"还是"是客户端库内部状态问题"**:`redis-cli` 直连验证服务端;`monitor`/`client list` 观察客户端行为模式,两者交叉对比能快速定位问题域
- **同一个连接 id 持续存在但停止活动 = 卡死;连接 id 变化/消失 = 断开重连**,这个区分本身就是很有信息量的诊断依据
- **不要在早期证据不足时就断言根因**,新证据出现要敢于推翻之前的假设(取消机制 → 并发访问,是两个完全不同的修复方向)

### 三个连接对象的线程安全边界,横向对比结论
|                                                 | 天生线程安全吗                                                                       | 需要做什么                      |
| ----------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------- |
| `grpc::Channel`                                 | **是**,官方明确保证,设计目的就是被多线程共享                                         | 不需要额外处理                  |
| `mysql::connection_pool`(设 `thread_safe=true`) | **是**(有一个已知边界:completion token 若手动 bind_executor 可能失效,目前用法没撞上) | 保持简单用法即可                |
| `boost::redis::connection`(裸用)                | **不是**,没有类似开关                                                                | 必须自己保证只被单线程/串行访问 |

## 二、Boost.Redis 响应类型的两个隐蔽坑

### 坑 1:响应类型必须跟 Redis 命令的实际返回类型精确匹配
- `SET`/`SETEX` 返回状态字符串 `"OK"` → 用 `response<std::string>`
- `HSET`/`INCR`/`DEL` 返回整数 → 用 `response<long long>`
- 填错(比如给 `SET` 填 `response<long long>`)会报 `"Can't convert string to number (maybe forgot to upgrade to RESP3?)"`——**这句提示是通用兜底文案,容易误导去查 RESP2/RESP3 协议版本,实际根因几乎总是类型填错,不是协议版本问题**

### 坑 2:响应解包是"两层"结构,不是"查个 ec 就完了"
```
response<T> → std::get<N>(resp) → result<T, adapter::error>
                                      ├─ .has_error()  → 协议/适配层面有没有出错(不是业务错误)
                                      └─ .value() → T(如果 T 本身是 optional<U>,还要再判断 .has_value())
```
- `GET` 这类可能返回 nil 的命令,`T` 必须是 `std::optional<U>`,`.has_value()` 判断的是"key 存不存在"这个**正常业务结果**,不是错误
- 普通 `SET`(无 `NX`/`XX`)不需要判断具体值,`has_error()` 过了就必然是 `"OK"`;一旦用到 `NX`/`XX`,合法返回值里多了"nil"这种情况,又要多加一层 `optional` 判断

### 排查新命令该填什么类型的捷径
不确定某命令返回类型时,直接 `redis-cli` 手动跑一次这条命令看返回值形态,比翻文档更快。

## 三、Boost.MySQL 的 NULL 列映射

- `static_results<T>` 会**逐列**比对数据库 schema 和 C++ 类型,只在"数据库允许 NULL 但 C++ 类型装不下"的那一列报错(不是整体拒绝)
- 修复:该列换成 `std::optional<T>`;转到对外业务类型时,按业务语义决定是保留 `optional` 还是用 `.value_or(默认值)` 合并处理(例如"好友备注"NULL 和空字符串语义等价,合并成空字符串是合理的)
- **排查习惯**:写新的 Row 结构体前,先逐列核对表 DDL 里的 `NOT NULL` 约束,不是 `NOT NULL` 的列默认都套 `optional`,不要等运行时报错才发现

## 四、多表联合查询:JOIN vs 事务,判断标准很清晰

- **纯读、多表关联查询 → `JOIN`**,一条 SQL 搞定,天然原子,不需要事务
- **多条写语句、要求"要么全成功要么全不生效" → 事务**(`BEGIN`/`COMMIT`/`ROLLBACK`),典型场景如"接受好友申请"需要同时更新申请状态 + 插入双向好友关系
- 数据库查询结果(扁平 Row 结构体)和对外业务类型(嵌套结构体)分两层,加字段只需要动 SQL 列表 + Row 结构体 + 组装那一行,不会牵连调用方接口定义

## 五、缓存一致性:Cache-Aside 模式下的竞态问题

### 问题本质
`GET 未命中 → 查库 → SET 回缓存`,这套流程非原子,中间若有并发写操作插入,可能导致缓存里写入的是旧值。

### 应对手段,按复杂度递进
1. **写操作删除缓存而非更新缓存**——最常用、最简单的缓解手段,把"更新缓存"这个多步骤操作换成"删除"这个瞬时操作,大幅缩小竞态窗口
2. **延迟双删**——更新库 → 立即删一次缓存 → 睡一会 → 再删一次,工程实用主义补丁,不是理论完美方案
3. **分布式锁串行化"查库+写缓存"**——能比较彻底解决,但引入锁的复杂度代价
4. **基于 binlog/CDC(如 Canal、Debezium)异步更新缓存**——从根源消除竞态窗口(缓存更新的唯一触发源是"数据库真正提交之后"),但架构复杂度显著上升,一般大规模项目才用

### 认知层面
- 缓存本质是用"强一致性"换性能,追求的目标应该是**最终一致性**,不是绝对实时一致
- TTL 的作用是给最终一致性**兜底**(哪怕脏了,过期后自愈),不是主动解决竞态的手段
- 策略选择要跟具体业务场景的一致性要求匹配,没有放之四海而皆准的"标准答案"——一般项目"删除缓存 + 合理 TTL"就够用

## 六、长连接场景下的身份验证设计

### 与短连接(HTTP/JWT)的本质区别
短连接每次请求独立、无状态,只能靠 token 自证身份;**长连接本身就是有状态的会话载体**,登录一次后,身份信息记在 session 对象上,后续消息不需要每条都带凭证。

### 具体设计要点
- **登录失败应直接断开连接**,不是"允许无限重试直到成功"——防暴力破解、防资源占用,这是安全默认值,不是过度设计
- **断开前必须确保错误响应已经真正发送出去**——不能在业务逻辑函数内部直接调用 `stop()`,因为消息发送是异步的(经过 channel 排队),必须让"发完就关"这个动作发生在真正执行写操作的地方(`writer()`),而不是消息生成的地方
- **实现手法**:让消息携带一个 `close_after_send` 标记随着消息一起投递,`writer()` 在真正写完这条消息后检查这个标记再执行关闭——这是处理"异步发送+发送后必须执行某动作"场景的通用模式
- **未登录连接需要独立的超时保护**(比如 10 秒内必须完成登录),跟"已登录后的空闲超时"是两个独立机制,分别防"连上不发消息"和"登录了但不活动"两种资源占用
- **`is_authenticated_` 这类状态标记只被单一协程(reader)读写时,普通 `bool` 就够,不需要 `atomic`**——原子操作是给"确实存在跨线程/跨协程并发访问"的场景准备的,不是无脑加

### 一个真实踩到的 bug
`check_login_deadline()` 这类独立的超时检测协程,必须通过 `co_spawn` 真正启动,直接调用只是构造了一个 `awaitable` 对象,协程体不会执行——这是"awaitable 惰性求值"这条规律在新场景下的再次复现,提醒自己:**任何返回 `awaitable<T>` 的函数,裸调用永远只是构造对象,必须 `co_spawn`/`co_await` 才会真正跑**。

## 七、gRPC 补充要点

- **request/response 在 `Finish()` 被调用之前始终有效**,不是"异步期间不能碰"这种笼统限制;但工程上更推荐的做法是**尽早把需要的字段从 request 提取成局部拷贝**,让业务逻辑跟 gRPC 对象生命周期彻底解耦,不用纠结"这次挂起会不会跨越到 Finish 之后"
- **gRPC 方法可能被自己的线程池并发调用多次**,官方文档明确要求"用到共享资源必须自己同步"——这条原则跟本项目一路遇到的并发保护问题(sessions_、redis 连接)是同一件事的不同体现
- **多个结构相似的 gRPC 回调 handler,可以把"查找目标 session + 投递通知消息"这段公共逻辑抽成模板函数**,不同的通知消息类型作为模板参数,避免三份几乎一样的代码分别维护

## 八、其他杂项

### `cancel_after` 补充理解
- `cancel_after(timer, duration)`(不显式传内层 token)会用一个默认 token,只要外层这次调用本身被 `co_await`,能正确解析成可等待的对象
- `redirect_error` 和 `cancel_after` 组合必须嵌套成一个 token(如 `redirect_error(cancel_after(10s, use_awaitable), ec)`),不能作为两个独立参数分别传给 `async_exec`——这类"多个 completion token adapter 要嵌套组合"的坑,这次是第二次踩,应该记牢这条规律

### `asio::consign`
completion token adapter,把一份对象(通常是 `shared_ptr`)的生命周期"绑定"到某次异步操作上,操作完成前这份引用不会被释放——用于替代手写 lambda 捕获 `shared_ptr` 来保活对象,是官方标准化的生命周期管理手段。

### `boost::thread_pool` 内部结构
是单一共享调度器(所有线程共享一个队列),不是每线程独立一个 io_context,跟之前项目里"多线程共享 io_context"的架构模型是同一类。

### 惊群问题澄清
只要是"单个 acceptor + async_accept 循环"模式,不管背后多少线程共享 io_context,都不存在惊群问题(任意时刻只有一次 accept 挂在 epoll 上)。惊群只在"多个独立进程/线程各自直接 accept 同一监听 fd"或者故意用 `SO_REUSEPORT` 建多个监听 socket 的架构下才需要考虑。

### 开发体验改善
- **clangd 插件**(非微软官方 C/C++ 插件)配合 `CMAKE_EXPORT_COMPILE_COMMANDS ON`,能提供接近 rust-analyzer 的悬停类型提示、inline 参数名提示
- **编译报错可读性**:优先切 clang 编译看报错(比 gcc 干净);gcc 可加 `-fdiagnostics-show-template-tree` 等参数优化模板报错;只看第一条 `error:`,后面的 `note:` 往往是级联信息
- **编译器选择必须放在 `project()` 之前**,`project()` 跑完后编译器就定死了,后面 `set(CMAKE_CXX_COMPILER ...)` 不生效;`CMAKE_CXX_COMPILER_ID` 要在 `project()` 之后才能读到
