# 测试计划

基于 `desc.md` 整理,在原有基本功能之外补充了边界/异常用例。表格里"自动化"一列标注了 `tests/` 目录里的 pytest 用例能不能覆盖。

## 环境准备(测试前置条件)

1. Redis、MariaDB 已启动,建好表(`user`/`friend`/`friend_apply`)
2. `verify_server`、`gate_server`、`status_server`、至少一个 `chat_server` 已启动
3. 测试跨服务器好友通知(用例 8.4、9.4)需要 `chat_server1` + `chat_server2` 都启动

## 通用设计说明

- 每次测试运行,用户名/邮箱都用随机后缀生成(如 `test_a1b2c3@test.local`),避免 `UNIQUE` 约束冲突,不需要在测试之间清空数据库
- 验证码通过直接读取 Redis(`GET <email>`)获取真实值,不依赖邮件发送
- 涉及"断连接"的用例,通过检测 socket 读到 EOF/RST 来判断,不依赖服务端日志

### 1.2 获取验证码

## 二、chat_server 长连接(TCP,MsgNode 协议)

### 2.1 连接与登录

| 用例 | 输入 | 期望 | 自动化 |
|---|---|---|---|
| 正常登录 | 合法 uid + token(1005) | 收到 1006,带 name/apply_list/friend_list | ✅ |
| token 不匹配 | uid 正确,token 错误 | 连接被服务端断开 | ✅ |
| 第一条消息不是登录 | 建连后先发 1007(搜索) | 连接被断开 | ✅ |
| 10s 内不发送任何消息 | 建连后什么都不发,等待 >10s | 连接被服务端主动断开 | ✅(耗时较长,标记为 slow) |
| 重复登录 | 同一条连接,登录成功后再发一次 1005 | 观察实际行为(当前逻辑下 reader 应该已经放行非登录消息,重复登录消息按普通消息处理,记录实际结果) | ✅(探测性) |

### 2.2 好友搜索

| 用例 | 输入 | 期望 | 自动化 |

### 2.3 好友申请

| 用例 | 输入 | 期望 | 自动化 |
|---|---|---|---|
| 正常申请(对方在线,同服务器) | uid 为自己,touid 为对方且在线 | 数据库插入 friend_apply,对方收到 1011 通知 | ✅ |
| 申请自己 | touid == 自己的 uid | 应被拒绝(文档要求 touid 不为自身) | ✅ |
| uid 字段与登录 uid 不符 | 消息里的 uid 不是这条连接登录的 uid(伪造) | 应被拒绝(防止冒充) | ✅ |
| 对方不在线 | touid 对应用户当前未连接任何 chat_server | 请求仍然成功(写入数据库),但不产生通知,不报错 | ✅ |
| 重复申请 | 同一对 (from,to) 重复发起 | 数据库 `UNIQUE(from_uid,to_uid)` 约束,应返回错误而不是崩溃 | ✅ |
| 跨服务器通知 | Client2 连在 chat_server2,Client1 在 chat_server1 上发起申请 | Server1 通过 grpc 通知 Server2,Client2 收到 1011 | ⚠️ 需要双 chat_server 环境 |

## 三、运行结果与发现(2026-08-08)

### 测试客户端修正

- **端序 bug**:`msg_node.py` 原本用小端 `<IH`,但服务端 `msg_node.hpp` 用 `boost::endian` 转大端。已改为 `>IH`。修之前 23 个 chat_server 用例全部失败(帧 id/长度反了,服务端直接断连)。
- **错误信封断言**:服务端错误响应是 `{"error":<码>,"message":<名>}`(无 `status` 字段);login 成功才用 `status`。新增 `conftest.is_ok()/is_error()` 统一判断。gate 对非法输入返回纯文本 `Invalid JSON body`(非 JSON),新增 `gate_ok()` 容忍。
- **断开类用例**:wrong token / 首条非登录 场景,服务端是先回一个错误帧再断开,不是直接 RST。测试已改为先读错误帧再 `expect_closed`。

### 服务端真实问题

1. **[已修复] token 校验漏洞**:`chat_server/handle_message.cpp` login 只检查 redis 里"有没有"该 uid 的 token,没比较请求里的 token 值——任何知道 uid 的人,只要目标用户登录过,就能用任意 token 登录。已修复(不匹配返回 `TokenInvalid` 1009)。
2. **[未修,保留失败] 重复好友申请静默成功**:`test_add_friend_duplicate` 失败。服务端 `add_friend` 对 `friend_apply` 唯一约束冲突不感知,继续走流程返回 Success。期望是拒绝或至少返回错误。
3. **[未修,保留失败] 认证不存在的申请静默成功**:`test_auth_friend_nonexistent_apply` 失败。服务端 `auth_friend` 对 `UPDATE ... WHERE from_uid/to_uid` 影响 0 行也返回 Success。期望是返回错误。

> 第 2、3 点按 README"用法提醒"的约定保留失败——它们用来暴露服务端该补的逻辑,不代表测试写错。
